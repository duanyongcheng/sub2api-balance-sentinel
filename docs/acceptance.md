## 2026-10-23 安全修复与文档复核

- 监控创建与编辑分离：重复创建返回 `409`，不会覆盖停用状态、审批模式、备注或规则版本；编辑 / 删除要求 `ruleRevision`。保存规则的 SQLite 写事务内重新检查会话、角色和凭据版本，等待上游查询期间撤权的旧请求不能继续保存。
- 账本绑定完整规范化基础 URL 与可选 `SENTINEL_INSTANCE_ID`。新空库初始化；已有未绑定库必须关闭加额并在可信本地明确确认。实例、基础路径或 ID 不匹配时，上游查询、身份刷新、规则变更与所有加额被拦截，原本地账本仍可查看；Key 轮换不影响绑定。
- 流水页面使用后端总数分页，支持用户 / 状态筛选；独立「未决处理」包含 `pending` / `unknown`，旧未决流水不会被 200 条新成功记录挤掉。过期的列表 / 证据请求不能覆盖新筛选结果。
- 通知按渠道确认成功：企业微信 / 钉钉 `errcode: 0`，飞书 `code: 0` 或旧 `StatusCode: 0`，Slack 纯文本 `ok`；矛盾、缺失或畸形响应不报告成功。generic 仅确认 HTTP 成功，不承诺远端业务处理。通知拒收和日志故障不会改变加额结果，更不会触发加额重试。
- 新增回归位于 `instance-binding.test.js`、`rule-safety.test.js`、`notify.test.js`、`web-ledger.test.js`；既有测试夹具显式绑定虚构实例，保留原资金与认证断言。
- 本机实际 Node `v25.9.0`：完整 `npm test` 329 项通过；前端生产构建、5 项 Python 集成工具安全测试、JS / MJS 语法检查和 `git diff --check` 通过。项目未配置独立 lint / 类型检查，不将语法解析当作这些检查通过。
- `npm audit` 完整依赖审计：0 项已知漏洞；不包含 OS 镜像扫描或未披露漏洞。
- 独立本地启动验证使用真正的 `index.js`、本机模拟上游和临时账本：登录、实例绑定、重复创建 `409`、观察模式审批拒绝均通过，模拟余额保持 `5`；服务收到 `SIGTERM` 后以 `0` 退出。验证进程与临时账本已清理，没有连接真实 Sub2API。

## 部署边界

尚未连接用户现有 Sub2API、配置生产域名 / 反向代理、进行生产部署或独立安全审计。上述软件与隔离测试证据不替代这些环境工作。

上线前由部署者完成：

1. 确认实际 Sub2API 版本、管理员 API Key 权限、幂等去重和余额历史行为。管理员合规确认必须自行阅读和处理，工具不会替真实管理员接受条款。
2. 在受保护的服务器文件 / Secret 中注入凭据。不要通过聊天、命令参数、工单或日志交付 Key；不要给哨兵上游数据库账号。
3. 保持默认 loopback 发布；远程使用 HTTPS 反向代理并启用 HSTS，设置 `AUTH_SECURE_COOKIES=true` 与精确的 `ALLOWED_HOSTS`，优先叠加 VPN / 来源限制。
4. 妥善保管初始管理员恢复材料和数据卷的受保护备份；如果主动启用 TOTP，账户加密密钥与账本分开保管。Linux 上只允许容器 UID 1000 与必要运维身份读取挂载的 Secret。
5. 先保持 `AUTO_TOPUP_ENABLED=false` 观察，核对用户与金额，再用测试用户完成一次真实收支核验，最后按业务需要开启自动加额。
6. 正常停止使用 Compose 的宽限期。强杀、断电或超时后，保留并核实 `pending` / `unknown`，不要清空未决记录或自动补发。
